What the seven checks look for

A PDF can describe itself in more than one place, and the visible properties panel only shows the first one. These are the seven that matter, in the order the checker reports them:

  1. Info dictionary. /Title /Author /Subject /Keywords /Creator /Producer plus the two dates. This is what the properties panel shows, and the only place most cleaners touch.
  2. Info dictionaries nothing points to. A cleaner can reset the trailer's /Info pointer and still leave the old dictionary standing in the file as an object with no reference — the author name is gone from the panel and still in the bytes. This check reads the raw bytes for /Author, /Title, /Subject, /Creator, /Producer and /Keywords values that do not match what a viewer shows.
  3. Referenced XMP packet. An XML block reached through the catalog's /Metadata entry. It usually repeats dc:creator, xmp:CreatorTool and pdf:Producer.
  4. Orphaned XMP. Deleting the pointer does not delete the packet. Cleaners that only unlink /Metadata leave the XML sitting in the file as an unreferenced stream; this check enumerates every indirect object and decompresses it to look. It is the difference between "the properties panel is empty" and "the bytes are gone".
  5. Retained revisions. PDF is append-only, so each save can leave the previous version behind. Two or more %%EOF markers means earlier revisions are still in the file, and an earlier revision is an earlier author name.
  6. Page-level and document-level extras. /PieceInfo from layout tools, and /EmbeddedFiles attachments — both carry names that never appear in the properties panel.
  7. Producer fingerprint. "Microsoft Word 2016" or "iLovePDF" on its own identifies which machine class and which tool handled the file, even with the author field blank.

Why a checker and not another cleaner

Every online tool grades its own homework. In the nine-tool comparison behind this site, PDF2Go emptied the Author field in the properties panel while dc:creator and xmp:CreatorTool stayed in the XMP packet, PDF Candy reset the trailer's Info pointer and left the original dictionary standing as object 18 with nothing pointing at it, and PDFgear returned the original /Producer string byte for byte. All three look clean to anyone who reopens the file and glances at the properties.

Our own first pass got this wrong, which is the honest reason this page exists. The 9-tool table was first read with a byte search, because that is what a hex editor gives you. Three tools came back clean that way — Sejda, PDF24 and Xodo — and all three had kept every Info field; the names were inside compressed object streams, invisible to a byte search and perfectly visible to a viewer. The table has been re-read with a full parser and corrected. A checker that cannot disagree with its author is decoration.

So this page does not clean anything. It reports, and it reports the unreferenced leftovers that a cleaner's own success message cannot see. Run it on the file you were about to send, or on the file a tool just handed back: the 9-tool test tells you which tools are worth checking first.

If a name is in the body text rather than the metadata, no checker will help — that is a redaction problem, and the redaction tool removes the text instead of covering it.

Limits, stated plainly

  • Checks 2, 5, 6 and 7 read raw bytes, so a dictionary packed inside a compressed object stream can be missed. The report says "not found", not "absent". Checks 1, 3 and 4 parse the object graph instead, which is how the compressed-stream case is caught at all.
  • XMP streams larger than 5 MB, and files larger than 64 MB, are reported as unscanned rather than counted as clean.
  • The checker never writes to the file. If the report finds a leak, fixing it is a separate step.
  • Metadata is one leak, not all of them: fonts, page geometry and the text itself are untouched by any of this.

Metadata questions

How is this different from the remove-metadata tool?

The remove tool rewrites the file and clears both channels. This page only reads it. Keeping them separate is the point: a cleaner that also grades itself is the failure this page was built to catch.

Does it work on a file another tool already compressed?

Yes, and that is the main use. Compression is not metadata removal: several tools in the 9-tool test returned files with the original author or producer intact. Run the checker on the download before you send it anywhere.

What is an orphaned XMP packet?

When a cleaner deletes the catalog's /Metadata reference, the XML stream itself can remain registered as an object and get written back on save. The properties panel shows nothing; the bytes still contain the author. This check decompresses every stream to find that case.

What is an orphaned Info dictionary?

The trailer's /Info entry is a pointer, not the dictionary itself. A cleaner that resets the pointer leaves the original dictionary in the file as an object nobody references: the properties panel shows new values, the old author name is still on disk. PDF Candy's output in the 9-tool test does exactly this — object 18, 216 KB into a 226 KB file, carrying the original /Author and /Producer.

Are my files uploaded?

No. The file is read from disk into memory and parsed in the browser. No request leaves the machine, and no copy is stored.
