I compressed the same file in 9 PDF tools. Seven handed a version of my name back.

One 1.27 MB probe PDF with five unique strings written into it, one action (compress), nine browser tools, output read with a full parser and re-read byte by byte. Last tested 21 November 2026.

Short version

7 of 9 tools returned a file carrying /Author = INDEX PROBE 2026 somewhere, the name I typed into the probe. Six kept it in the Info dictionary that the properties panel reads — iLovePDF, Sejda, PDF24, PDF Candy, Xodo and PDFgear. PDF2Go blanked the field and left the same name in the XMP packet.

4 of 9 left the original producer string in the file. PDFgear, PDF24 and Xodo returned PRIVACY-INDEX-PROBE-PRODUCER character for character in the Info dictionary; PDF Candy reset its panel to "PDF Candy" and left the old dictionary standing as object 18. Image streams were recompressed; the document dictionary rode along.

Clearing the Author field is not deleting the name. PDF2Go is the case to remember. Open the properties panel and it looks empty. Search the raw bytes and the name is still there.

How the probe works

I wrote a 12-page A4 PDF filled with per-page noise images, 1.27 MB, so that compression actually has something to remove. Into its Info dictionary I wrote five strings that could not occur by accident:

  • /Author (INDEX PROBE 2026)
  • /Title (Probe Document for Privacy Index)
  • /Subject (PRIVACY-INDEX-2026-PROBE)
  • /Creator (Privacy Index Test Harness)
  • /Producer (PRIVACY-INDEX-PROBE-PRODUCER)

The same four values were also written into an XMP packet, so a tool that clears one and keeps the other would be caught. Each output was read three ways: the Info dictionary as the document a viewer opens, the presence of an XMP packet, and a raw byte search for all five strings. A tool is only marked "clean" when all three are empty. The byte search is the weakest of the three, which is what the correction note above is about: values can sit inside compressed object streams where no byte search will ever see them.

This is deliberate over-testing. Field-only checks are what a property panel shows you, and a property panel is exactly what PDF2Go defeated.

Three findings worth keeping

1. The blank field is the trap PDF2Go

PDF2Go removed /Author from the Info dictionary and left the XMP packet in place. That packet still contained <dc:creator><rdf:li>INDEX PROBE 2026</rdf:li> and <xmp:CreatorTool>Privacy Index Test Harness</xmp:CreatorTool>. The Title and Subject were kept too. If you judge a file by the properties dialog, this output passes. It is not clean.

Rule of thumb: a partial scrub is worse than no scrub, because it stops you from looking. "Author is empty" answers a different question than "the name is gone".

2. Recompressing images is not touching the dictionary PDFgear, PDF24, Xodo

All three returned the five fields exactly as written, including /Producer, which almost every other tool replaces with its own name. The most likely explanation is mechanical, not malicious: the tool rebuilds image streams inside the existing document rather than rebuilding the document, so the Info dictionary travels with the pages. The files got 78% to 94% smaller and the author name came along for the ride. Xodo's case is the instructive one: 189 KB of output, every string still readable, and not one of them present as plain bytes, because all of it sits inside a compressed object stream.

PDF Candy is the same failure with a better disguise. Its properties panel shows "PDF Candy" as Creator and Producer, and the original /Author and /Producer are still in the file — as object 18, sitting 216 KB into a 226 KB document, referenced by nothing. Anyone who opens the file sees a clean panel. Anyone who reads the bytes sees the probe.

3. Clean and aggressive are different things Adobe

Adobe's online compressor took the file from 1.27 MB to 28.4 KB, a 98% cut, and returned no Info fields and no XMP packet. That is the strongest result in the table, and also the least gentle: at that size the noise images have been resampled hard. It also allowed an anonymous download, no account, which is worth noting because the page says files are processed on Adobe servers and deleted unless you sign in to save them.

Where the tools refused to be compared

Three sites could not produce a comparable output, and the reason matters as much as a metadata result:

  • Soda PDF compressed the file, then replaced the download with "Create an account or sign in to instantly download your file". The free tier also only offers Regular compression, with the stronger setting marked Pro. No account, no output, nothing to inspect.
  • Foxit's online tool returned Application error: a client-side exception has occurred on two loads from this network. No upload interface, no test.
  • HiPDF rendered only its navigation layer and never reached a file picker.

Rows like these are not failures of the index. "You cannot get the file back without an account" is a privacy-relevant fact about the service, and it belongs next to the metadata column.

Check your own output in one command

You do not need my probe to run this. Take any PDF you have already processed, and search its raw bytes for a name you know is in it:

strings yourfile.pdf | grep -i "your name"

If that prints a line, the name is still in the file, even if the properties dialog shows an empty author. For the structured version, read both places explicitly:

# pip install pypdf
from pypdf import PdfReader
r = PdfReader("yourfile.pdf")
print(r.metadata) # Info dictionary
root = r.trailer["/Root"]
print("/Metadata" in root) # XMP packet still attached?

A blank r.metadata with /Metadata present means somebody cleared the visible fields and left the packet, which is the PDF2Go shape. Both empty is the shape you want.

Limits of this test

Stated plainly, because an index that hides its gaps is just marketing:

  • Upload evidence is indirect. I can show that the result came back from the service after a pause, and that the page describes server-side processing, but I did not capture the network requests. So "the file left the device" is documented and structural here, not packet-level proof.
  • Desktop tools are not in the table. Ghostscript was tested separately on the same probe: it replaced /Producer and left /Author, /Title, /Subject, /Creator and the XMP packet intact. A desktop program is not automatically the private option.
  • One file, one action, one date. A tool can change its pipeline next week. The date at the top is the only guarantee.
  • This site's own tools are not in the table. I am not going to grade my own compressor with a friendlier method than the one I used on everyone else. When it can be measured under the same conditions, it goes in the same table.

Questions this test answers

Does compressing a PDF remove the author name?

Not reliably. Six of the nine tools tested returned the name, in the Info dictionary, in an unreferenced dictionary, or in the XMP packet. If the file is going to a client, a court or a public post, compress first and then run a metadata check on the output, not on the input.

Why does the properties panel show no author when the name is still there?

Because PDFs store the name in two places. The panel reads the Info dictionary; the XMP packet is a separate XML block attached to the document catalog. A tool can empty the first and never look at the second.

Which tools were cleanest in this test?

Adobe Acrobat online and Smallpdf were the only two that returned no Info fields and no XMP packet; Smallpdf left its own producer string ("Pdftools SDK") in the dictionary. Adobe also cut the file the most, which is a separate question from privacy and worth weighing separately.

Is a desktop tool automatically safer than an online one?

No. Ghostscript, running entirely on the machine, kept the author, title, subject and creator and only replaced the producer. "Nothing was uploaded" and "nothing identifying is left" are two different claims.

Do the other half yourself

If you are about to send a PDF out, the order that works is: compress with whichever tool you like, then check, then clean if the check fails.
